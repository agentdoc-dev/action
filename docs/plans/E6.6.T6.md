## Paired transport contract

Two request headers on each actual attempted POST:

- `x-agentdoc-egress-policy-digest`: exactly the lowercase digest returned by the immediately preceding successful source-bound policy check for that POST's required categories.
- `x-request-id`: fresh canonical UUID per **HTTP attempt**, reusing Cloud's existing request-correlation convention if the final Cloud inspection confirms each relevant route accepts/preserves it. It differs on retry while body and business Idempotency-Key remain byte-identical. If any legacy route cannot accept that existing header, root must freeze its minimal route plumbing before execution; do not invent a competing body identity.

No header value comes from model text, selected repository content or ambient caller-supplied digest. Digest is captured from `check()`'s verified response; UUID is generated in the trusted helper. Add both to the same private curl config as authorization. Do not add curl retries: rerunning an uploader must recheck policy and mint a fresh attempt ID.

Cloud/native partner reports that registration may truthfully record **authenticated receipt of the body under the sender-reported and currently verified policy**, while a later ingestion/finalization phase may still refuse after policy changes. Therefore the transport acknowledgment cannot mean business admission or execution success. A native receiving receipt is not an approval, completed ingestion, synchronization or dispatch fact. All later native phases continue to compare the expected digest with current policy under existing locks.

Suggested minimal response acknowledgment: the existing `x-request-id` plus `x-agentdoc-egress-policy-digest`, set together only after the receiving fact for that exact operation/body/request ID is persisted. This requires an explicit Cloud/native invariant; an automatic HTTP correlation header or fresh policy GET header alone is insufficient. Action marks the receiving fact confirmed only when the final response block contains exactly one matching request ID and exactly one matching checked digest. Cloud may carry this receiving acknowledgment on a later business refusal if it already persisted the earlier receipt; that is accurate, not success. Missing/malformed/mismatching acknowledgment leaves receiving status unconfirmed; it must not be replaced with a policy digest fetched after upload.

This transport metadata does not add a public JSON envelope. The accepted paired plan requires a valid declared digest on Cloud payload/notice endpoints; mismatches fail closed. An old server's body-only success may preserve the existing business status but cannot count as T6 receiving evidence. Do not silently call that path T6-compatible.

Cloud facts record sender-reported policy and authenticated current receiving authority; they do not prove that arbitrary external clients actually executed a GET. The trusted Action and real sequential HTTP tests establish its own check→send behavior.

## Private per-attempt evidence

Keep existing status files and closed bodies unchanged. Use a unique file per attempt under a private mode0700 child of `ADOC_RUN_DIR`; create files exclusively with mode0600, write via a private temporary file and atomically finalize the same attempt. A subsequent retry always gets a new UUID/path and never overwrites earlier completed attempt metadata. No durable queue/journal/recovery framework is needed.

Small internal fields only: operation, Workspace/repository UUID, HTTP attempt/request ID, exact outgoing request digest, optional existing business idempotency key, checked_policy_digest, transport observation, curl return code, HTTP status, native receiving acknowledgment state, and existing validated business outcome/code. Include no credentials, payload text, raw response/error, source excerpt, free-form remediation or user-controlled header text. Result's **HTTP body digest** is distinct from its nested result_digest and should be computed over the actual body_file before its existing deletion.

Distinguish these states precisely:

| Observation | Private evidence | Existing business status |
| --- | --- | --- |
| Check/refreshed authority denies before curl | Existing skipped/failed status; no payload-attempt sidecar claiming transmission | Unchanged |
| Prepared attempt but process dies before confirmed curl return | Prepared/unconfirmed; never assert bytes were sent or received | No invented success |
| curl returns an error/no trustworthy HTTP response | Delivery unconfirmed; retain checked digest and returned curl code only | Existing failed path |
| HTTP response observed, no matching native receiving acknowledgment | Response observed; native receipt unconfirmed | Existing closed-body validation still decides its business outcome |
| Matching native receiving acknowledgment, later domain rejection/partial result | Receiving confirmed; business refused/partial | Existing failed/partial status |
| Matching native receiving acknowledgment and valid accepted/duplicate response | Receiving confirmed; business accepted/duplicate | Existing completed status |

A receipt prepared before starting curl cannot truthfully set “transmitted=true”; local process death/DNS/TLS failure can happen before any bytes leave. The recorder provides stronger observed-send evidence in tests. Once curl returns, completion metadata records observations, not a fabricated count of server-persisted bytes. A receipt-write failure before attempting curl suppresses the attempt through existing failure handling; a failure after an HTTP attempt never rewrites it into “not sent.” Keep any prepared unconfirmed evidence. Parent must choose the exact small helper subcommand arguments during implementation; no payload should be passed through shell interpolation.

Parsing response headers should reuse the helper's existing final-HTTP-block/duplicate-header discipline. Accept no digest from trailers, intermediate blocks, duplicate headers, unrelated request IDs or unbounded content. Header dump files remain private and are removed after extracting whitelisted facts; raw headers never enter stdout/ordinary receipts.
